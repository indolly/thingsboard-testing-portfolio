### JMeter性能测试

- 使用`setUp Thread Group`只执行一次登录和设备查询，避免把认证开销混入目标接口；
- 负载线程循环请求`GET /api/device/{deviceId}`；
- 除HTTP 200外，还断言响应设备ID与目标ID一致；
- 线程等待固定为100 ms，逐级执行10、25、50、100、200、400、800线程；
- 使用每档最后10秒作为稳态窗口，排除升压阶段对吞吐的影响。

| 线程数 | 稳态请求数 | 失败数 | 平均响应 | P95 | 最大响应 | 稳态吞吐 |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 887 | 0 | 4.75 ms | 7 ms | 9 ms | 88.70/s |
| 25 | 2217 | 0 | 4.40 ms | 6 ms | 24 ms | 221.70/s |
| 50 | 4454 | 0 | 4.46 ms | 6 ms | 26 ms | 445.40/s |
| 100 | 8757 | 0 | 5.07 ms | 8 ms | 28 ms | 875.70/s |
| 200 | 16770 | 0 | 8.46 ms | 17 ms | 55 ms | 1677.00/s |
| 400 | 32743 | 0 | 9.58 ms | 20 ms | 60 ms | 3274.30/s |
| 800 | 42196 | 0 | 55.78 ms | 121 ms | 383 ms | 4219.60/s |

400至800线程时，线程数翻倍但吞吐只增长约28.9%，平均响应和P95分别增长约5.8倍和6.1倍，确认明显拐点位于400至800线程之间。全部档位虽然0失败，但800线程已经出现明显性能退化。

限制：JMeter与ThingsBoard运行在同一台电脑；只覆盖单一只读接口；每档只执行一次且持续时间较短。因此结果不能直接外推生产容量，正式测试需要独立发压机、重复执行和服务端CPU、GC、数据库连接池等监控。

## 4. 典型问题与闭环

| 问题 | 分类 | 处理与结果 |
|---|---|---|
| Postman通过代理访问`localhost`时连接异常 | 工具/网络环境 | 关闭Postman代理并使用`127.0.0.1`后恢复 |
| 误把50℃作为告警清除边界，恢复遥测已保存但告警不清除 | 测试预期 | 读取设备配置档案确认清除条件为`temperature <= 45`，使用45.1℃和45℃重新执行后通过 |
| Jenkins回归出现4个失败、30个初始化错误 | 环境 | 定位为Docker Desktop未运行、9091端口未监听；启动环境后回归成功 |
| 非法资产ID查询关系返回404而不是空数组 | 接口行为理解 | 根据实际API语义调整预期，保留404断言 |
| 客户用户读取已分配设备凭据返回200 | 测试预期 | 查阅本机OpenAPI后确认该角色被官方允许，改为验证未分配设备对象级越权 |
| JWT只修改末字符仍可能有效 | 测试数据 | Base64URL末字符可能只改变未使用位，改为修改签名段首字符 |

## 5. 产品缺陷记录

### TB-DEFECT-001 非法排序字段触发数据库异常并返回500

| 字段 | 内容 |
|---|---|
| 环境 | ThingsBoard Community Edition 4.2.1.1，Docker单节点，PostgreSQL |
| 严重程度 | 中等 |
| 优先级 | P2 |
| 状态 | 已确认，待产品修复 |
| 影响接口 | `GET /api/tenant/devices`、`GET /api/tenant/assets`、`GET /api/customers`、`GET /api/alarm/{entityType}/{entityId}` |
| 前置条件 | 使用租户管理员JWT访问实体列表接口 |
| 测试数据 | `pageSize=10&page=0&sortProperty=notARealField&sortOrder=ASC` |
| 预期结果 | 服务端校验`sortProperty`不属于OpenAPI枚举，返回400参数错误，不执行数据库排序 |
| 实际结果 | 四个接口稳定返回500，响应为`Database error`、`errorCode=46` |
| 服务端证据 | 日志出现`Could not resolve attribute`，分别指向`DeviceEntity`、`AssetEntity`、`CustomerEntity`和`AlarmInfoEntity` |
| 界面证据 | [Postman复现截图](../evidence/screenshots/invalid-sort-property-500.png) |
| 影响 | 非法客户端输入被错误归类为服务端故障，污染5xx监控；重复请求会产生数据库异常日志并增加无效处理开销 |

复现步骤：

1. 使用租户管理员账号登录并取得JWT；
2. 请求`GET /api/tenant/devices?pageSize=10&page=0&sortProperty=notARealField&sortOrder=ASC`；
3. 观察HTTP状态码和响应体；
4. 对资产列表、客户列表和设备告警列表执行相同参数；
5. 检查ThingsBoard服务端日志。

当前处理：

- 已使用Postman手工执行设备接口，结果为500；
- 已横向手工验证资产、客户和告警接口，结果均为500；
- 已与本机OpenAPI合法排序字段枚举核对；
- 已保存4个独立复现请求，方便产品修复后执行关联回归。

闭环进度：`发现 → 稳定复现 → 排除环境和脚本问题 → 横向验证 → 定位异常层 → 登记`已完成；`产品修复 → 修复验证 → 关联回归 → 关闭`等待后续版本。
